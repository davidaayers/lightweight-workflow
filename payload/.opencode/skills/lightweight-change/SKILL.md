# Lightweight Change

Read `.opencode/workflow/project.md` for project owners/overrides and
`.opencode/workflow/policy.md` for execution decisions. This skill owns the
operational procedure, not product guarantees or project verification commands.

## Start Or Resume

1. Reuse the request, conversation, handoff, or named active plan. Inspect the
   working tree, affected code/tests, and relevant current owners from the adapter.
   Search its active-plan locations for concrete overlap in paths, owners, or scope;
   read selected records in depth. Exclude archives from routine context. Preserve
   applicable pending obligations and explicit user decisions.
2. Investigate discoverable facts. Apply **Plan For Consequences** when a material
   decision emerges; retain the decision and relevant compatibility/failure/check
   evidence in the existing record before affected implementation.
3. Proceed when implementation is requested and scope is clear. Create an optional
   brief from `brief.md` at the adapter's location only when persistence helps.
   Check active/archive name collisions, retain its notice and active status, and
   never overwrite another record or duplicate the supplied plan.
4. On resume, reconcile the selected record with current owners and code. Recorded
   checks are not automatically fresh. Resume an ongoing UI session's scoped diff
   and conversation record rather than restarting discovery.

## Build And Verify

- Implement small observable end-to-end increments with acceptance from the request.
  Update incidental implementation details as evidence changes.
- Reconcile affected contracts, current design, implementation, and relevant tests.
  Read complete affected guarantees and named direct dependents. Use the adapter's
  decision/history conventions where applicable; report unrelated drift separately.
- Run the adapter's file-appropriate checks and inspect rendered evidence for visual
  work. Reuse passing evidence until relevant edits/failures invalidate it. Derive
  test expectations from intended behavior, not implementation output.
- Keep decisions, actual evidence, and blockers in the conversation or existing plan.
  Missing/failed required checks leave work pending; continue safe independent work.

## Iterative UI Work

Use the policy's checkpoint timing and declared guarantees. Establish named surfaces,
baseline, owners, and overlap once. Keep accepted tweaks, changed paths, pending
reconciliation, and evidence in conversation. Use the project's local feedback
tooling. Retain the record and pending state on pause/handoff.

## Finish

1. Inspect accumulated scoped changes, including new files. Confirm acceptance,
   affected current-owner agreement, and required checks. Rerun only affected/failed
   evidence. For UI iteration, do this at the selected checkpoint.
2. Apply **Review Selection** through `code-review`. Supply the request/record,
   scoped diff, owners/direct consumers, and evidence. Record findings/resolutions
   in conversation or the existing record; directly verify focused corrections.
3. Report scope, outcome, checks/review, and concrete gaps. Record genuinely deferred
   obligations in the adapter's backlog/issue owner. If a brief exists, fill its
   Completion with actual disposition, set terminal status, and safely relocate it
   below. Brief-less work has no archive task.

## Saved Brief Closeout

Move the same record to the adapter's historical location. Preserve contents and
root-relative references. Check the destination; never overwrite it. On collision,
use an unused suffixed name and report it. Confirm the destination exists and active
source is absent before completion. A failed move with source remaining restores
active status and records a closeout blocker; retry without repeating valid checks.
For cancellation or user-accepted supersession, record the actual disposition and
replacement link before relocation. Never mark unfinished work complete.
